# Независимое ревью PDFCompare Local — 2026-07-13

Проверенная ревизия: `db8c1d95f4150749dfa19e36389d7e9b80ca7a08` (`master`, рабочее дерево было чистым перед записью этого отчёта).

## 1. Резюме

Проект находится в хорошем для локального инженерного инструмента состоянии: движок разделён на осмысленные модули, статические проверки жёсткие, тесты быстрые, а core покрыт на 88,18%. На чистом Python 3.12.10 из `requirements/lock.txt` прошли ruff, mypy и все 154 теста; PyInstaller 6.21.0 также собрал EXE. Математика миллиметровых зон и физических метрик использует эффективный DPI после megapixel-cap и в проверенных сценариях корректна. Основные оставшиеся риски сосредоточены не в алгоритме диффа, а на границах жизненного цикла: откат при ошибке самого восстановления, принудительная отмена MCP-перегенерации и миграция старых percent-зон через новый редактор. Транзакционный happy path и обычные failpoint-ошибки защищены заметно лучше прежнего, но аварийное завершение процесса пока не является частью модели транзакции. Hash-lock действительно используется обоими CI-job, однако автоматически обновляемый MCP-чекаут устанавливает свободные диапазоны и потому не получает той же воспроизводимости. Критических дефектов, немедленно затрагивающих каждый запуск, не найдено; до следующего релиза рекомендую закрыть три `major`-находки ниже.

### PDF-001 — старые percent-зоны не сохраняют смысл при редактировании

Внутренняя модель редактора всегда миллиметровая, а переключатель единиц всегда инициализируется значением `mm` (`exclusion_picker.py:250`). Импорт старого значения сначала переводит percent в пиксели выбранного листа, затем в mm (`:506-516`); при OK весь набор экспортируется в текущей общей единице (`:844-851`). Исходная единица региона нигде не сохраняется.

Сценарий воспроизведения:

1. В `state.json`, истории или поле GUI оставить старую область `70,80,30,20`.
2. Открыть редактор на A4 portrait и, ничего не меняя, нажать OK.
3. Фактический результат в проверке: `{"x":146.93,"y":237.6,"w":63.07,"h":59.4,"unit":"mm","anchor":"top_left"}` вместо прежних 70/80/30/20 percent.
4. На A0 portrait старая зона занимала бы примерно 252×238 мм, а новая остаётся 63×59 мм. То есть последующее сравнение исключает другую часть листа.

Это особенно опасно потому, что исключения непосредственно влияют на отсутствие/наличие найденных изменений. Переключатель `mm` виден пользователю, но обычное «открыть и подтвердить» не воспринимается как миграция данных.

Рекомендация: для однородного существующего набора инициализировать единицу его исходным значением и не менять сериализацию без явного переключения. Для смешанных наборов либо хранить unit на каждом внутреннем регионе, либо показывать явное подтверждение миграции. Добавить регрессионные тесты «open → OK без изменений» для percent/mm, всех четырёх anchors, portrait/landscape и нестандартного размера.

### PDF-002 — rollback удаляет backup, если восстановление backup не удалось

`_RunUpdateTransaction.rollback()` восстанавливает metadata через `shutil.copy2`, но любой `OSError` игнорируется (`runner.py:611-615`), после чего staging безусловно удаляется (`:616`). Это расходится с правильной политикой `generate_html_report`: если восстановление старого report bundle не удалось, backup намеренно оставляется как последняя копия (`html_report.py:1867-1878`).

Сценарий воспроизведения подтверждён отдельной негативной проверкой:

1. Сохранить `summary.json` со значением `OLD` через `preserve_file()`.
2. Перезаписать live-файл значением `NEW`.
3. При rollback подменить `shutil.copy2` на `OSError("locked")`, имитируя блокировку файла/ошибку диска.
4. После rollback live-файл остаётся `NEW`, staging отсутствует, backup отсутствует. Единственная старая копия потеряна.

Рекомендация: считать неудавшееся восстановление ошибкой rollback, собирать список невосстановленных файлов и не удалять их backups/staging. Исходное исключение и ошибку восстановления нужно связать в диагностике. Добавить failpoint именно на restore, а не только на ошибку перед rollback.

### PDF-003 — принудительная MCP-отмена обходит транзакционный unwind

GUI передаёт `cancel_cb`, поэтому Python получает `RunCancelled` и выполняет `rollback()`. MCP устроен иначе: worker вызывает `regenerate_report_pages_mixed()` без cancel callback (`pdfcompare_worker.py:155-175`), а `cancel_pdf_comparison()` завершает дерево через `taskkill /F` (`pdfcompare_mcp.py:1036-1039`). Принудительно завершённый процесс не выполняет `except/finally`, а транзакция существует только в памяти.

Сценарий воспроизведения:

1. Запустить через MCP перегенерацию нескольких листов существующего отчёта.
2. Дождаться стадии после `_replace_page_dirs_from_staging()` (`runner.py:1008`), когда новые страницы уже live, а старые лежат в `.rerender_*/backup_pages`.
3. Вызвать `cancel_pdf_comparison` до `txn.commit()` (`runner.py:1055`).
4. Worker уничтожается немедленно; в зависимости от момента остаются новые страницы со старым summary/report либо частично обновлённые metadata и `.rerender_*`. MCP cleanup удаляет только `<out_dir>/.pdfcompare_mcp_<job>`, не журнал внутри run.

Рекомендация: для MCP использовать кооперативный cancel marker (например, файл в job-dir), передав worker-у `cancel_cb`, и лишь после таймаута переходить к force-kill. Дополнительно нужен дисковый transaction journal и recovery при следующем открытии/перегенерации, потому что crash/power loss возможны независимо от отмены.

### PDF-004 — added/removed страницы имеют только один checkpoint отмены

В matched-ветке проверки стоят между render A, render B, alignment, diff и записью. В ветке added/removed есть только `check_cancelled()` на `runner.py:427`, после чего последовательно выполняются full render, preview render и записи PNG (`:428-444`). Негативная проверка с флагом, который взводится после первого опроса, вернула обычный `added`-результат, выполнила только один cancel-check и записала два PNG.

Рекомендация: добавить checkpoints после каждого full/preview render и перед каждым блоком записей; включить added и removed в spawn/cancellation тесты.

### PDF-005 — MCP bootstrap не использует lock

CI действительно устанавливает `requirements/lock.txt` с `--require-hashes` в test и build (`build-exe.yml:48-50`, `:77-79`). Но MCP bootstrap вычисляет stamp только из `base.txt`, `mcp.txt` и HEAD, затем вызывает `setup.ps1 -WithMcp`; setup устанавливает свободные диапазоны (`setup.ps1:19-21`). Поэтому один и тот же commit MCP может завтра получить другой NumPy/OpenCV/PyMuPDF/MCP, хотя CI для этого commit останется зелёным на lock-наборе.

Рекомендация: для автоматически управляемого MCP-чекаута ставить `requirements/lock.txt --require-hashes`; loose-файлы оставить только сознательным developer entry point. Stamp должен включать hash lock-файла и версию Python.

### PDF-006 — non-stdio guard не обеспечивает заявленный allowlist

`resolve_path()` разрешает любой абсолютный путь текущего пользователя (`pdfcompare_mcp.py:78-88`). `main()` блокирует non-stdio только до установки `PDFCOMPARE_MCP_ALLOW_NETWORK=1`; никакой allowlist после этого не проверяется (`:1052-1059`). Если транспорт доступен не только доверенному localhost-клиенту, инструменты позволяют читать произвольные PDF и писать результаты в произвольный каталог.

Статус `needs-verification`: фактическая удалённая экспозиция зависит от bind/auth-настроек FastMCP 1.28.1 и окружения запуска; сетевой сервер в рамках ревью не поднимался. Тем не менее сообщение guard-а утверждает наличие условия, которого код не исполняет.

Рекомендация: либо полностью запретить non-stdio в поставляемом entry point, либо требовать и применять нормализованный input/output allowlist (с проверкой resolved path и symlink/junction escape), а также документировать authentication/bind.

### PDF-007 — MCP-документация отстала от нового picker

Реальный MCP tool прямо документирует mm-результат (`scripts/pdfcompare_mcp.py:930-943`), но `docs/LOCAL_AGENT_MCP.md:42` говорит «percent units», а два готовых agent prompt требуют собирать percent-boxes от top-left. Это направляет агента к ровно той модели, от которой свежая версия отказалась из-за масштабирования штампа.

Рекомендация: сделать mm + anchor рекомендуемым путём во всех трёх документах, percent оставить явно как legacy/scaling option; добавить docs-consistency assertion хотя бы на ключевые фразы/сигнатуры MCP tools.

### PDF-008 — навигация отчёта масштабируется как O(N²)

Каждый slider view проходит по всем `pages_records` и строит собственный `slider_nav_html` (`html_report.py:654-736`). Отдельно один полный `nav_html` встраивается в каждую detail page (`:1824-1847`). Для N листов получается O(N²) повторяющихся DOM-узлов и байтов; golden fixture из двух листов этого не выявляет.

Рекомендация: сначала измерить bundle size/generation/open time на 100/300/1000 листах. Инкрементальный вариант без сборщика: общий `report.json` + небольшой JS-рендер списка на клиенте или отдельный shared navigation fragment, загружаемый локально. До изменения зафиксировать performance budget.

### PDF-009 — неизвестная единица становится percent

В `_normalize_region_values` только ratio/relative и px/mm распознаются явно; всё остальное попадает в ветку `else` и становится `percent` (`exclusions.py:140-147`). Это удобно для отсутствующего unit, но небезопасно для присутствующего ошибочного unit.

Рекомендация: default применять до вызова нормализации, а неизвестное непустое значение отклонять с перечнем допустимых aliases.

## 3. Оценка решений

| Решение | Оценка | Аргумент |
|---|---|---|
| Зоны в mm от anchor по умолчанию | **Согласен, с обязательной миграционной оговоркой.** | Это правильная модель для физических штампов. Core-математика при разных DPI/форматах корректна; проблема только в потере исходной percent-семантики при round-trip через picker (PDF-001). |
| FG% + композитная классификация и sparse fallback | **Согласен.** | FG% решает искажение пустым полем листа, а mm²/число зон страхуют почти пустые страницы. `runner.py:343-376` передаёт фактический effective DPI, `diff_engine.py:151-174` считает физические площади из него. |
| Статический HTML с inline CSS/JS | **Согласен для offline/local продукта.** | Нет runtime/server-зависимости и отчёт переносим. Риск — рост дублированной навигации O(N²) и сложность тестирования монолитных шаблонов (PDF-008). |
| GUI mixins + `AppProtocol` | **Есть архитектурный риск, но текущий рефакторинг полезен.** | Миксины уменьшили `_build_ui`, strict mypy ловит рассинхронизацию. Одновременно `AppProtocol` уже около 250 строк и описывает большую часть объекта приложения (`contracts.py:25-258`), то есть граница остаётся «god-interface». Следующий шаг — не новые mixins, а небольшие state/service-контракты. |
| MCP workers + status.json, auto-pull master | **Workers/status — согласен; auto-pull — риск.** | Отдельный процесс изолирует тяжёлый OpenCV и сохраняет статус для агента. Но force-kill небезопасен для in-place rerender (PDF-003), а auto-pull вместе с loose install делает запуск недетерминированным (PDF-005). |
| Per-user Inno + `/SILENT`, SHA-256 без Authenticode | **Приемлемый осознанный риск для доверенного круга.** | Проверка hash защищает от повреждения/несовпадения assets, но manifest и installer имеют один GitHub trust root. Не следует описывать это как аутентичность издателя. Код корректно не запускает installer без совпавшего hash (`pdfcompare_gui.py:1350-1375`). |
| Golden hashes/snapshot как страховка рефакторинга | **Хороший characterization layer, но не основной функциональный тест.** | Report golden фиксирует RU/EN HTML/JSON и проверяет детерминизм; GUI golden фиксирует дерево первого запуска. Они не проверяют команды/callbacks, picker, геометрию/цвета/DPI, added/removed/mixed reports и большие N; текущая миграция percent также не покрыта. |
| Кооперативная отмена между фазами | **Согласен для GUI/core.** | Это безопаснее принудительного завершения и разумно ограничивает latency. Нужно довести checkpoints до unmatched-веток (PDF-004) и привести MCP к той же модели (PDF-003). |

Решения, которые важно не потерять при исправлениях:

1. Предварительный megapixel-cap и использование единого effective DPI для обоих растров и всех mm/mm²-метрик (`pdf_io.py:44-64`, `runner.py:339-379`).
2. Построение отчёта во временном bundle и сохранение старого bundle/start.html до успешной публикации (`html_report.py:1711-1717`, `:1850-1883`), плюс failpoint fingerprint всего затрагиваемого набора.
3. Один hash-lock для CI test/build и Actions, закреплённые commit SHA (`build-exe.yml:35-50`, `:64-79`, `:111-124`).

## 4. Что проверено и как

### Карта репозитория

- Язык приложения — Python; GUI — Tkinter/tkinterdnd2; PDF — PyMuPDF; image/diff — NumPy + OpenCV.
- HTML/CSS/JavaScript генерируются Python-кодом без frontend build step.
- Автоматизация — PowerShell; CI — GitHub Actions YAML; инсталлятор — Inno Setup; EXE — PyInstaller.
- Точки входа: `compare_pdfs.py` / `python -m pdfcompare_core` (CLI), `pdfcompare_gui.py` (GUI), `scripts/pdfcompare_mcp.py` (MCP), `scripts/pdfcompare_worker.py` (background worker).
- Основные границы: `pdfcompare_core/` (domain/engine/report), `pdfcompare_ui/` + `pdfcompare_gui.py` (desktop UI), `scripts/` (операционные entry points), `packaging/`, `tests/`, `docs/`.
- CI: test job выполняет lock install → lint → tests; build зависит от test и собирает EXE/portable/installer/SHA256/release assets.

### Ограничения проверки

- GitHub Actions и опубликованные release assets не запрашивались из GitHub независимо; вывод о workflow основан на локальном YAML и локальном воспроизведении test/build.

- EXE собран, но полноценный интерактивный smoke frozen-GUI и frozen multiprocessing/cancel не автоматизирован.
- CVE-аудит по внешней advisory-базе не выполнялся; проверены hash-lock и `pip check`, но это не заменяет `pip-audit`/OSV.
- Не проводился браузерный performance benchmark отчёта на 100+ реальных листах; PDF-008 выведен из подтверждённой структуры вложенных генераций и требует пороговых измерений.
