# Промпт для полного ревью PDFCompare Local

Скопируйте текст между линиями и отправьте ревьюверу (AI-агенту или человеку), добавив актуальный путь к репозиторию.

---

Ты — старший инженер, проводящий независимое ревью репозитория **PDFCompare Local**. Твоя задача — проверить весь репозиторий и оценить принятые архитектурные решения, а не только найти опечатки. Работай с кодом напрямую: читай файлы, запускай проверки, подтверждай каждую находку конкретным местом в коде.

Репозиторий: `<ПОЛНЫЙ ПУТЬ К РЕПОЗИТОРИЮ>` (Windows, Python 3.12, venv в `.venv`).

## Что это за проект

Локальное Windows-приложение для сравнения двух ревизий PDF (чертежи/схемы): Tkinter GUI, рендер через PyMuPDF, дифф через OpenCV/NumPy, результат — статический HTML-отчёт (матрица изменений, просмотр листа, слайдер OLD↔NEW). Плюс CLI, MCP-сервер для AI-агентов (фоновые worker-процессы), сборка EXE (PyInstaller), Inno Setup инсталлятор с тихим автообновлением, CI на GitHub Actions.

Карта кода:
- `pdfcompare_core/` — движок: `runner.py` (оркестрация прогонов и перегенерации), `diff_engine.py`, `alignment.py`, `classification.py` (FG %, уровни изменений), `exclusions.py` (зоны исключения: percent/mm/px + якоря углов), `html_report.py` (~2900 строк: генерация всего HTML/CSS/JS отчёта), `pdf_io.py`, `cli.py`, `constants.py`.
- `pdfcompare_gui.py` + `pdfcompare_ui/` — GUI: миксины (`rerender_tab`, `history_tab`, `dnd`, `state_persistence`) с типовым контрактом `contracts.AppProtocol`, визуальный редактор зон `exclusion_picker.py`, `i18n.py` (RU/EN словари), `update_check.py` (автообновление через GitHub Releases).
- `scripts/pdfcompare_mcp.py` — MCP-сервер (FastMCP, stdio), `scripts/pdfcompare_worker.py` — фоновый worker.
- `packaging/` — PyInstaller spec + `installer.iss`; `.github/workflows/build-exe.yml` — CI; `tests/` — pytest; `docs/` — документация.

## Как запускать проверки

```powershell
.venv\Scripts\python.exe -m ruff check .
.venv\Scripts\python.exe -m mypy compare_pdfs.py pdfcompare_gui.py pdfcompare_core pdfcompare_ui
.venv\Scripts\python.exe -m pytest -q
```

Не запускай `git push`, не меняй код — ревью только читает и пишет отчёт.

## Области проверки (по убыванию важности)

1. **Корректность движка**: `diff_engine`, `alignment`, `classification`, `exclusions` — граничные случаи (пустые/повёрнутые/разноформатные страницы, зоны с якорями на страницах разных размеров, округления процентов около 100), согласованность метрик FG % / мм² / зон между runner, HTML/markdown-отчётами и GUI-таблицами.
2. **Целостность прогона**: атомарность записи отчёта (staging/rename в `runner.py`, `html_report.py`), поведение при отмене/крэше worker-а, перегенерация страниц (uniform/mixed) — не портит ли она соседние страницы и summary.json.
3. **MCP-сервер**: управление фоновыми процессами (PID-проверки, cleanup устаревших задач), безопасность (`resolve_path`, запуск подпроцессов, guard на не-stdio транспорт), совпадение поведения инструментов с GUI (исключения зон текстом/JSON/якоря, rerender-переопределения).
4. **GUI**: потокобезопасность (worker-события через queue, обращения к Tk только из главного потока), персистентность состояния, редактор зон (`exclusion_picker.py`) — геометрия перевода px↔%↔мм, якоря, поведение при нестандартных DPI/масштабировании Windows.
5. **Автообновление и упаковка**: скачивание и тихий запуск инсталлятора (`update_check.py`, `_download_update_installer`, `installer.iss`) — сценарии сбоя (обрыв сети, занятые файлы, запуск из portable EXE), корректность per-user установки, CI-workflow (сборка EXE/ZIP/инсталлятора, публикация релиза).
6. **HTML-отчёт**: JS слайдера/матрицы (утечки обработчиков, поведение при 100+ листах, localStorage-ключи), CSS-грид с пришпиленной панелью, container queries, embed-легаси, i18n RU/EN переключение.
7. **Качество кода и архитектуры**: оправданность миксин-архитектуры с `AppProtocol`, размер и связность `html_report.py` (~2900 строк) и `runner.py`, дублирование между `live_report`/`html_report`/`markdown_report`, покрытие тестами слабых мест (GUI почти не покрыт, MCP — только импорт).
8. **Документация**: README / CHANGELOG / docs соответствуют коду (форматы зон, флаги CLI, инструменты MCP, процесс релиза).

## Ключевые решения — оцени каждое (согласен / есть риск / предлагаю иначе, с аргументами)

- Зоны исключения в процентах как канонический формат поля + якоря углов; mm/px поддержаны на входе.
- FG % (доля изменённого от нарисованного) как главная метрика + композитная классификация (FG % / мм² / число зон) с фолбэком для «пустых» страниц.
- Статический HTML-отчёт с инлайн CSS/JS без сборщика и внешних зависимостей.
- Миксины + Protocol-контракт вместо наследования/композиции для GUI.
- MCP: отдельные worker-процессы со status.json-файлами вместо потоков.
- Per-user Inno-инсталлятор + самообновление через /SILENT с перезапуском.
- Проверка обновлений раз в час.

## Формат отчёта

Пиши ревью в Markdown-файл `docs/reviews/<YYYY-MM-DD>_review.md` (создай папку при необходимости). Структура:

1. **Резюме** — 5–10 предложений: общее состояние, главные риски.
2. **Находки** — таблица + детали по каждой:
   - `ID | Серьёзность (critical/major/minor/nit) | Область | Файл:строка | Суть`;
   - для critical/major — сценарий воспроизведения: какие входные данные/действия приводят к какому неверному результату;
   - рекомендация по исправлению (без переписывания кода за автора).
3. **Оценка решений** — по списку выше, коротко и аргументированно.
4. **Что проверено и как** — какие команды запускал, что прочитал целиком, а что по диагонали (честно).

Правила: не выдумывай находки — каждая должна опираться на прочитанный код; если не уверен — помечай `needs-verification` и объясняй, чего не хватает; ложные срабатывания хуже пропусков. Хвалить не нужно, но отметь 2–3 удачных решения, чтобы их случайно не «исправили» в будущем.
