Скопируйте текст между линиями и отправьте ревьюверу (AI-агенту или человеку), добавив актуальный путь к репозиторию.

Ты — старший инженер, проводящий независимое ревью репозитория **PDFCompare Local**. Проверь весь репозиторий и оцени принятые решения, а не только опечатки. Работай с кодом напрямую: читай файлы, запускай проверки, подтверждай каждую находку конкретным местом в коде.

Репозиторий: `<ПОЛНЫЙ ПУТЬ К РЕПОЗИТОРИЮ>` (Windows, Python 3.12, venv в `.venv`).

## Что это за проект

Локальное Windows-приложение для сравнения двух ревизий PDF (чертежи/схемы): Tkinter GUI, рендер через PyMuPDF, дифф через OpenCV/NumPy, результат — статический HTML-отчёт (матрица изменений, просмотр листа, слайдер OLD↔NEW). Плюс CLI, MCP-сервер для AI-агентов (фоновые worker-процессы), сборка EXE (PyInstaller), Inno Setup инсталлятор с тихим автообновлением, CI на GitHub Actions.

Карта кода:
- `pdfcompare_core/` — движок: `runner.py` (оркестрация прогонов, перегенерации, отмены), `diff_engine.py`, `alignment.py`, `classification.py`, `exclusions.py` (зоны: percent/mm/px + якоря углов), `html_report.py` (генератор отчёта: `generate_html_report` — оркестратор, `_build_dashboard_html`, `_write_page_views`, `_write_slider_view`, контекст `_ReportContext`), `html_fragments.py` (`ReportI18n`, `ReportBadges`), `html_css.py` (все стили), `pdf_io.py`, `cli.py`, `constants.py`.
- `pdfcompare_gui.py` + `pdfcompare_ui/` — GUI: миксины (`compare_tab`, `rerender_tab`, `history_tab`, `dnd`, `state_persistence`) с типовым контрактом `contracts.AppProtocol`, визуальный редактор зон `exclusion_picker.py`, `i18n.py` (RU/EN), `update_check.py`.
- `scripts/pdfcompare_mcp.py` — MCP-сервер (FastMCP, stdio), `scripts/pdfcompare_worker.py` — фоновый worker, `scripts/run_mcp_bootstrap.ps1` — запуск с автообновлением из git.
- `packaging/` — PyInstaller spec + `installer.iss`; `.github/workflows/build-exe.yml` — CI (hash-lock зависимостей, Actions по SHA); `tests/` — pytest (включая golden-тесты); `docs/`.

## Как запускать проверки

```powershell
.\scripts\lint.ps1     # ruff + mypy (hard gate; не strict)
```

Не запускай `git push`, не меняй код — ревью только читает и пишет отчёт.

## На что обратить особое внимание (свежие изменения)

Это места, где ошибка наиболее вероятна и наиболее дорога:

1. **Единицы зон исключения.** Визуальный редактор теперь отдаёт зоны в **миллиметрах от угла привязки** (`unit: "mm"`), а не в процентах. Мотив: зона в процентах не переносится между форматами — штамп 185×55 мм, обведённый на A4, на A0 превращается в 741×220 мм. Проверь: математику `exclusions.exclusion_regions_to_pixel_boxes` для mm+anchor при разных DPI и размерах листа; модель редактора (`region_rect_mm` / `region_from_rect_mm` / `region_to_export`); совместимость со старыми сохранёнными значениями (в state.json и истории лежат проценты); поведение при повёрнутых страницах и нестандартных размерах (сканы).
2. **Отмена сравнения.** Флаг отмены доезжает до воркеров пула через `initializer/initargs` (spawn-Event по наследованию, не через `submit`). Проверь: нет ли гонок; корректно ли всё разворачивается (частичная папка удаляется, staging не остаётся); работает ли отмена в frozen-сборке (PyInstaller + `freeze_support`).
3. **Транзакционность отчёта.** Бандл отчёта и `start.html` публикуются вместе; при ошибке восстанавливается предыдущий отчёт. Проверь `html_report.py` (финальный swap) и `_RunUpdateTransaction` в `runner.py` на предмет путей, где бэкап может быть потерян.
4. **Golden-тесты как страховка рефакторинга.** `tests/test_html_report_golden.py` (хеши всего HTML/JSON отчёта) и `tests/test_gui_layout.py` (снапшот дерева виджетов). Оцени: достаточно ли они строгие, что именно они НЕ покрывают, не маскирует ли нормализация (таймстемпы, пути, размер PDF) реальные регрессии.
5. **Воспроизводимость сборки.** `requirements/lock.txt` (hash-pinned) ставится в обоих CI-job; Actions прибиты по commit SHA. Проверь, что версии из исходников (`base.txt`/`dev.txt`) и из лока не разъезжаются.

## Области проверки (по убыванию важности)

1. **Корректность движка**: `diff_engine`, `alignment`, `classification`, `exclusions` — граничные случаи (пустые/повёрнутые/разноформатные страницы, зоны с якорями на листах разных размеров и ориентаций, округления около 100%), согласованность метрик FG % / мм² / зон между runner, HTML/markdown-отчётами и GUI-таблицами. Учти megapixel-cap: физические метрики должны считаться от **эффективного** DPI, а не запрошенного.
2. **Целостность прогона**: атомарность записи отчёта, поведение при отмене/крэше worker-а, перегенерация страниц (uniform/mixed) — не портит ли она соседние страницы и summary.json; карантин упавших прогонов.
3. **MCP-сервер**: управление фоновыми процессами (PID-проверки, cleanup), безопасность (`resolve_path`, запуск подпроцессов, guard на не-stdio транспорт), паритет инструментов с GUI, автообновление из git (`run_mcp_bootstrap.ps1`) — что будет при грязном рабочем дереве, конфликте, обрыве сети.
4. **GUI**: потокобезопасность (Tk только из главного потока, события через queue), персистентность состояния и истории (все ли параметры восстанавливаются), редактор зон — геометрия px↔мм, якоря, поведение при Windows-масштабировании (125%/150% DPI) и на многостраничных PDF.
5. **Автообновление и упаковка**: скачивание и тихий запуск инсталлятора, SHA-256 проверка манифеста, сценарии сбоя (обрыв сети, занятые файлы, запуск из portable EXE), per-user установка, CI-workflow.
6. **HTML-отчёт**: JS слайдера/матрицы (утечки обработчиков, 100+ листов, localStorage), CSS-грид с пришпиленной панелью, i18n RU/EN.
7. **Качество кода и архитектуры**: оправданность миксин-архитектуры с `AppProtocol` (он разросся — не превратился ли в «god-интерфейс»), результат разбиения `html_report.py` и `_build_ui`, дублирование между `live_report`/`html_report`/`markdown_report`, покрытие слабых мест (GUI покрыт снапшотом, MCP — тонко).
8. **Документация**: README / CHANGELOG / docs соответствуют коду (форматы зон, флаги CLI, инструменты MCP, процесс релиза).

## Ключевые решения — оцени каждое (согласен / есть риск / предлагаю иначе, с аргументами)

- **Зоны в мм от угла привязки как формат по умолчанию** (проценты остались опцией); текстовое поле принимает проценты, JSON с mm/px и якорями.
- FG % (доля изменённого от нарисованного) как главная метрика + композитная классификация с фолбэком для «пустых» страниц.
- Статический HTML-отчёт с инлайн CSS/JS без сборщика.
- Миксины + Protocol-контракт для GUI.
- MCP: отдельные worker-процессы со status.json вместо потоков; автообновление MCP-чекаута из master при каждом старте.
- Per-user Inno-инсталлятор + самообновление через /SILENT; SHA-256 без Authenticode (осознанный риск, распространение среди своих).
- Golden-тесты (хеш вывода отчёта, снапшот дерева виджетов) как основной способ безопасного рефакторинга UI/отчёта.
- Отмена через общий флаг, опрашиваемый между фазами страницы (кооперативная, не принудительная).

## Формат отчёта

Пиши ревью в Markdown-файл `docs/reviews/<YYYY-MM-DD>_review.md` (создай папку при необходимости). Структура:

1. **Резюме** — 5–10 предложений: общее состояние, главные риски.
2. **Находки** — таблица + детали:
   - `ID | Серьёзность (critical/major/minor/nit) | Область | Файл:строка | Суть`;
   - для critical/major — сценарий воспроизведения: какие входные данные/действия приводят к какому неверному результату;
   - рекомендация по исправлению (без переписывания кода за автора).
3. **Оценка решений** — по списку выше, коротко и аргументированно.
4. **Что проверено и как** — какие команды запускал, что прочитал целиком, а что по диагонали (честно).

Правила: не выдумывай находки — каждая должна опираться на прочитанный код; если не уверен — помечай `needs-verification` и объясняй, чего не хватает; ложные срабатывания хуже пропусков. Хвалить не нужно, но отметь 2–3 удачных решения, чтобы их случайно не «исправили» в будущем.
